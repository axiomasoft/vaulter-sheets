# Владение данными электронных книг

Установочные SQL PostgreSQL 18 соответствуют задачам. В 4.2 устанавливается [одна таблица команд](sql/sheets.sql), в 4.3 — [одна таблица обмена](sql/sheets-exchange.sql), в 5.1 — [семь таблиц чтения](sql/sheets-projections.sql), в 6.1 — [одна таблица связей совместной работы](sql/sheets-realtime.sql) поверх единого протокольно-нейтрального журнала `vaulter-collaboration` (`v_collaboration_heads.protocol = 'univer-sheets/1'`, `v_collaboration_updates`, `v_collaboration_receipts`). Обмен и проекции можно установить в любом порядке после 4.2. Каждая колонка, её тип, NULL, default, PK, FK, CHECK, UNIQUE, индекс и действие при удалении заданы в SQL. Ниже — смысл записей, момент появления, писатель, читатель и порядок отказа/очистки. По этим определениям пишутся install migrations закрытого `axiomasoft/vaulter-sheets`; пакет сохраняет настройки Vaulter для именования таблиц, соединения и стратегии ключей. Профиль SQL использует UUIDv7 в качестве внутреннего ключа Vaulter и bigint для tenant/subject. Остальные стратегии проверяются отдельными установками Laravel на поддерживаемых комбинациях. [Размещение пакета и runtime](../implementation/sheets.md)

## Что является источником

Рабочий JSON v2 (или лёгкий JSON-manifest со ссылкой на сжатый CAS-блоб `vaulter-media` при размере снимка выше порога `> 512 КБ`) лежит в `v_document_payloads.content`, ревизии — в `v_document_revision_payloads.content`. Внешний ID в Office SDK — ID узла Drive. Его разрешают через `v_documents.node_id` с повторной проверкой области доступа; `v_documents.id` — PK, на который ссылаются все перечисленные доменные таблицы. Поколение и позиция приходят от Documents, а тип, форма снимка и правила его изменения — от Sheets. В первом профиле обёртка содержит полное нативное содержимое (inline либо через CAS-блоб), точный профиль и sidecar логических таблиц/ID. Ограничения на индексах и компоновка вложенных строк не заменяют авторизацию.

В 1.1 Sheets переносит тип и слот со старым opaque-снимком. Дополнительных таблиц на этой ступени нет. В 4.2 устанавливается таблица команд. При появлении обмена файлами в 4.3 добавляется таблица заданий, в 5.1 — производные таблицы чтения. Блок `0006NN` зарезервирован за Sheets; имена установочных миграций ниже указаны относительно `packages/sheets/database/migrations/`, префикс имени файла `0001_01_01_`, окончание `.php`. Удобно ставить `000608` для exchange после создания ранее разрешённых номеров; Laravel записывает исполненные миграции по уникальным именам. Опциональный realtime устанавливает свою пару только при явном включении пакета/профиля; переход режима управляется доменом и не требует runtime на обычном snapshot-стенде.

| Имя миграции без префикса и расширения | Запись и основные обращения |
| --- | --- |
| `000600_create_v_sheets_commands_table` | Одно намерение или его компактный терминальный исход. `CommitWorkbookCommand` пишет, owner worker и API status/verify читают. Scope содержит tenant, проект, тип субъекта, id субъекта и document PK. Тип субъекта различает, например, user:7 и service:7. Уникальность command_id относится к полному scope. Отдельный уникальный receipt_id позволяет найти сохранённое доказательство с проверкой доступа |

Параллельные сборки могут иметь разные id; публикация выполняется только для подходящей текущей основы. `calculated_position` — подтверждённый расчёт в том же поколении, может быть NULL или отставать |

| `000605_create_v_sheets_projection_columns_table` | Устойчивый ID и заголовок колонки, абсолютный номер столбца. В одной именованной таблице каждая физическая колонка занята один раз |
| `000606_create_v_sheets_projection_rows_table` | Аналогично, устойчивый ID строки и актуальный абсолютный номер. Индекс по `(build_id,table_id,row_no)` даёт упорядоченное чтение и проверку состава таблицы. При структурной вставке строится соответствие из нового авторитетного sidecar |
| `000607_create_v_sheets_projection_cells_table` | Разреженная проекция. Один ключ `(build_id,sheet_id,row_no,column_no)`. Прямоугольник выбирается диапазоном строк и условием по столбцу. Короткий список логических row/column ID сначала превращается в ограниченные адреса. Формула отделена от введённого literal, рассчитанного значения/ошибки и текста отображения. Отсутствующая строка таблицы ячеек означает пустое значение, когда само положение существует; метаданные именованных строк от этого не зависят |

Дублирующих таблиц голов/обновлений у Sheets нет |

## Транзакции, повтор, восстановление и уборка

**Регистрация и повтор.** На POST/GET сначала разрешить публичный узел в доверенной области и проверить действующие права на исход операции. Потеря доступа даёт закрытый ответ. Владелец книги хранит исход UI, импорта и Office SDK в `v_sheets_commands`. Для POST вычислить fingerprint неизменяемого входа: версия и тело типизированной команды с исходным маркером/If-Match либо идентичность принятого AI-предложения и его digest. Текущие режим, generation, позиция, время и lease в fingerprint не входят. При регистрации использовать полный уникальный ключ из DDL. После конкурентного `INSERT … ON CONFLICT DO NOTHING` перечитать строку отдельным запросом на READ COMMITTED. Поиск существующего исхода выполняется до проверки свежести исходного маркера и выбора писателя. GET status определяет исход только по удостоверенному scope и ключу.

| Найденная запись | Ответ и действие владельца |
| --- | --- |
| POST с отличающимся fingerprint, включая истёкшую запись | `409 idempotency_conflict`. Первый исход сохраняется. `fingerprint` — SHA-256 RFC 8785 от `{commands, policy, if_match, expected_generation}`: та же команда под другой политикой (`exact_base`/`rebase_cells`/`revalidate_by_id`) — другой отпечаток. Квитанция в `evidence` хранит `structural_sheets`; по ним `rebase_cells` решает, можно ли перебазировать ([wire, §5](runtime-wire-v1.md#5-политики-владельца-при-движении-головы)) |
| Терминальная запись, текущее время достигло `replay_until`, или состояние `expired` | Для прежнего намерения и GET status вернуть `410 idempotency_window_expired` независимо от расписания уборки |
| `committed` или `rejected` до конца окна | Вернуть прежнюю квитанцию и маркер либо сохранённый отказ. При смене режима/restore у квитанции остаётся исходное поколение. Повтор обходится без вызова runtime, движения головы и новой записи в журнал |
| `running` | Вернуть статус ожидания. После истечения lease работник условно захватывает прежнюю запись, сверяет поколение, действующие права и исходные условия под блокировкой. Непринятая команда старого поколения завершается предусмотренным конфликтом |
| Ключ свободен | Зарегистрировать `running` с исходным намерением. Работник получает `worker_token` и lease. При фиксации повторно проверить token, состояние команды, полномочия и голову через протокол текущего писателя. Изменение Documents, исход команды, квитанция и outbox входят в один commit |

При завершении обработки (успех или доменный отказ) обновлять по внутреннему PK найденного намерения с условиями `state=running`, точного `worker_token` и `lease_until > clock_timestamp()` в PostgreSQL. Часы БД проверять после получения блокировки в транзакции владельца. При нуле обновлённых строк откатить рабочий результат и перечитать состояние команды. Условия действуют и до выдачи следующей аренды.

**Удержание.** При терминальной фиксации задать `replay_until` от момента завершения, чтобы длительное ожидание работника не поглотило окно получения исхода. При готовом расчёте `evidence` содержит формулы и значения. При ожидающем расчёте закрепить Media pin и `evidence_blob_id` точного исходного снимка. Срок `evidence_until` проверяется при выдаче. По истечении убрать доказательство, ссылку и pin. Для `verify(at_commit)` может использоваться ещё доступная авторитетная версия, иначе вернуть `evidence_unavailable`. По истечении окна повтора убрать intent/evidence и связанные pins, перевести запись в `expired`. До окончательного удаления книги сохранять scope, key, fingerprint и UUID выданной квитанции, на которую могут ссылаться журнал и задание импорта. Сроки определяет потребитель.

**Чтение.** В первой реализации каждая опубликованная сборка неизменяема. Проектор создаёт `building`, наполняет каталог и cells из одного снимка в согласованном профиле. При совпадении текущего поколения/позиции и digest завершает `ready` и условно двигает head. Читатель фиксирует согласованное состояние документа и head в одном запросе/транзакционном снимке, строит диапазон по одному build_id, сверяет ACL перед выдачей. Если `calculated_position < requested_position` или NULL, допускается новое авторизованное чтение runtime либо `calculation_pending`. Пустой литерал, отсутствующая вычисленная величина и вычисленный JSON null различаются: для последнего хранится JSONB `null`, SQL NULL означает «значение не записано». Даже ненулевой кэш из сериализации считается проверенным только после барьера расчёта. Сборку после записи стоимости одной ячейки измерить отдельно до включения на больших книгах; copy-on-write chunks или инкрементальные проекции требуют отдельного теста эквивалентности и смены projector_version.

**Restore/удаление.** До переключения читатель проверяет generation у Documents, поэтому старый head сразу перестаёт удовлетворять чтению. Предыдущие физические состояния и квитанции относятся к прежнему поколению, старый worker проигрывает CAS и не публикует запись. Из восстановленного payload заново строятся каталог, sidecar и ячейки. GC удаляет просроченные незаконченные сборки и старые готовые сборки, отличные от активного head; попытка удалить активную сборку без смены указателя отклоняется. Работы cleanup ограничены batch и повторяемы; чтение одной страницы фиксирует снимок БД, необработанный курсор на уже очищенную сборку возвращает ошибку срока. Штатный Drive purge в одной транзакции удаляет агрегат и публичный узел. Срабатывает CASCADE записей книги. Повтор по прежнему node ID получает закрытый ответ `404 resource_unavailable` на этапе авторизации. Создание и копирование выделяют новый node ID. Restore из корзины или ревизии сохраняет идентичность и реестр команд. [Порядок физического удаления](../../../packages/drive/src/Actions/Trash/PurgeNodeAction.php)

**Обмен.** Каждый импорт адресован уже авторизованной книге; для импорта в новую книгу fixture сначала создаёт пустую книгу, затем пользователь явно запускает import. Исходный блоб закрепляется через штатные Media pins. Пишется уникальное задание по доверенному scope и request key; один и тот же ключ с иными options/блобом отклоняется. Для экспорта перед постановкой сохранить и закрепить неизменяемый исходный снимок по `source_blob_id` с маркером запрошенной версии; если пользователь успел поменять рабочее состояние, экспорт выдаёт запрошенное состояние. Worker атомарно связывает принятый импорт с `v_sheets_commands` по детерминированному ключу от ID задания; после падения восстанавливает исход и report до отметки успеха. У успешного импорта `result_receipt_id` ссылается на квитанцию именно этой книги/поколения; успешный экспорт содержит `output_blob_id`. При экспорте защищаются основной и промежуточный исходник, пригодный для воспроизведения задания. Владелец сначала освобождает references/pins и удаляет/очищает запись exchange одним согласованным действием, затем обычная уборка Media может удалить уже не используемый объект. При физическом каскаде удаления документа отдельная процедура Media сверяет осиротевшие owner pins по их типу/ID до физической уборки. Ошибка экспорта не изменяет книгу.

**Realtime.** После переключения `v_documents.write_mode` в journal все источники записи, в том числе агент и UI, проходят через фиксированный fence документа. Объявленная типом поддержка протокола не переводит существующий document из snapshot в journal. Проверка фактического режима и поколений выполняется под блокировкой владельца. В транзакции владельца сверить generation, fence, head_seq, текущую позицию и входную команду. Освобождённый ресурс нельзя изменить запоздалым worker. Записываются exact bytes, их позиции и маркер владельца в одном commit с канонической версией и квитанцией. После падения проигрываются те же байты, пользовательский текст команды заново не исполняется. Compaction сначала строит бинарный checkpoint вне блокировки, сверяет его SHA и основание, внутри транзакции условно двигает checkpoint_seq, затем чистит только покрытый журнал с учётом удерживания offline клиентов и истории. Клиент за горизонтом получает свежий checkpoint. Для пустого checkpoint использовать документированный начальный бинарный снимок движка.

## Проверки для ревью

| Сценарий | Обязательный исход |
| --- | --- |
| Направить head на building либо на ready-сборку другого документа | Транзакция отклоняется FK даже при существующих UUID. При штатной публикации reader читает один build_id |
| Вставить коллизию абсолютного номера строки двух логических ID или cell с заполненными literal и formula | Срабатывают UNIQUE и CHECK, первая запись сохранна |
| Поставить committed без квитанции; записать одинаковый ключ с разным планом; повторить под другим субъектом | Невалидное состояние отвергается БД; обработчик сравнивает fingerprint в одном scope. Другой субъект не получает результат первого |
| Потеря ответа, истечение lease, повтор по tombstone, восстановление generation N+1 во время построения N | Единственный эффект и квитанция до истечения окна; после окна `idempotency_window_expired`; устаревшая сборка не становится активной |
| Удалить активную сборку, затем физически удалить документ | Первая операция отклоняется до commit. Во второй удаляются строки соответствующего документа и каскадные проекции; соседняя книга сохраняется |
| Закрыть процесс сразу после принятия нативной операции и до рассылки | Следующий fenced owner воспроизводит принятые байты в том же порядке; квитанция и canonical marker совпадают |

Выполнить `psql -X -v ON_ERROR_STOP=1 -f scripts/ci/sql/sheets-checks.sql` на отдельной БД после установки перечисленных SQL-файлов (`packages/sheets/database/sql/sheets_*.sql`), с подключением к нужной БД через обычные переменные libpq. Скрипт создаёт синтетические drive/node/document, читает формулу по логическим ID, проверяет ограничения, сохранение/повтор квитанции, защиту от ссылки импорта на другую книгу и detach при удалении. При установленном optional DDL дополнительно испытывает fence и повтор физической операции. Заканчивается ROLLBACK. [Воспроизводимая проверка](../scripts/ci/sql/sheets-checks.sql)

Локальный отдельный PostgreSQL 18.4 принял в порядке core → media → drive → documents → collaboration → collaboration-agent → sheets → sheets-exchange → sheets-projections → sheets-realtime все SQL-файлы проекта и создал 10 таблиц Sheets (включая тонкую `v_sheets_realtime_links` поверх единого журнала `vaulter-collaboration`) с 0 неиндексированных FK. Проверяющий скрипт выполнен дважды, до и после добавления realtime. После него число строк drives и commands совпало с исходным нулём. Тесты через реальные классы пакетов, профили ID и переключение режимов входят в приёмку реализации.
